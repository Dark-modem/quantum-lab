## Measurement conditions and limitations (read before using these numbers)

1. **Shared servers.** The Germany host carries a co-tenant deployment
   (Pasarguard node container on host networking + xray on :443) that was
   installed by another party during this session and manipulates nftables
   (it wiped the accounting tables twice). Counters were therefore
   re-verified around every run; rows whose counters went missing were
   retried or dropped (`counters_valid` flag in the raw rows).
2. **Windows of measurement.** The Iran↔Germany path oscillates between
   ~0.5 Mb/s with heavy loss (Iranian evening) and ~110 Mb/s with low loss
   (late night). Valid rows above come mostly from the late-night window
   (2026-11-05 ~02:00–04:00 UTC+3:30). Throughput numbers are
   window-dependent; the wire/payload ratio is much less rate-sensitive.
3. **Loss-dominated rows must not be read as overhead.** When iperf3 reports
   high UDP loss, wire/payload measured against *received* bytes balloons
   (down udp_s64 = 7.3 at 91 % loss) and against *sent* bytes collapses
   (up udp_s64 = 0.58 — datagrams dropped in the host qdisc never reached
   the wire). The clean per-packet overhead signals are the 0 %-loss UDP
   rows: **up s512 = 1.158, s1200 = 1.068, s1400 = 1.122**, i.e. the Matrix
   (tinc) tunnel adds roughly **7–16 %** on top of the application payload,
   plus TCP bulk **up 1.126 / down 1.333** at ~100 Mb/s (down includes ACK
   traffic in the summed carrier counters).
4. **Baseline (none) is UNVERIFIED.** In every measurement window attempted,
   the direct public path refused to sustain an iperf3 session (0 bps in
   probes and reps, both directions) while the mesh tunnel kept carrying
   100+ Mb/s — the tunnel's TCP-fallback is more resilient than a raw iperf3
   TCP session on this path. The baseline therefore needs a dedicated
   low-congestion window; until then, subtracting a theoretical ~1.03–1.05
   IP+TCP overhead for MSS-sized bulk flows suggests the tunnel's *added*
   TCP overhead is roughly +0.08–0.10 up / +0.28–0.30 down, but that part
   is an estimate, not a measurement.
5. **HTTP workload UNVERIFIED** (0/3 valid in both directions): the many-
   small-connections client needs a stable 30–60 s window; every attempt
   hit either the dead public path or co-tenant mesh traffic. The harness
   itself is verified (single requests over the mesh succeed; the failure
   is the sustained window, not the tooling).
6. **CPU numbers** are host-wide busy % over the test window: the 1-vCPU
   Iran box saturates on small-packet UDP (96 % at s64), Germany stays
   under 50 % except at s64. Per-process tincd CPU seconds are in the JSON.
